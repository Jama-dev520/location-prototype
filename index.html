Vendor Location List

One Source, not two — the type and its owner travel together: PUDOpoint (PUDO), packagehub (LMS), M&MP. Because the pair is a single field, an impossible type/source combination is not a filter you can build. What the providers actually sent us — every field is read-only, including sweeper, which now arrives with the daily sync. M&MP stores are self-operated, so their owner is the store itself rather than a provider — and LMS is who picks up for them. When a value is wrong, we do not correct it here: we flag it with a reason, the flag travels on this record, and the provider fixes the source. The OC layer only decides whether the location goes live.

OC Location List

One Source: packagehub (LMS) · PUDOpoint (PUDO) · M&MP — what it is and who owns it in one field. The record customers see. Two actions only: enable, and flag an anomaly. There is no editing here — a wrong address does not get typed over, it gets flagged back to the provider. Values are merged per field: an M&MP self-operated store is its own source and wins first, then LMS, then PUDO Inc fills whatever is still empty.

Duplicate Check

A standalone page for one question only: are these two vendor locations the same store? Pairs are detected by fuzzy match (address 50 · postal 25 · city 15 · state 10, threshold 75%). The two records are shown side by side, one row per field, with the differing part of each value marked, so the decision is read off the screen. The decision decides the mapping — same store = 2:1 (two vendor records, one OC location, LMS values win), not the same = 1:1 (each gets its own OC location). Every OC location that is fed by more than one vendor record is marked 2:1 in the OC list.

Data Issues

Everything that is wrong with the data, in one ledger — no review queues. It opens with the four checks operations chases every day — incomplete address, no postal code, no opening hours, a day open under three hours — each counted on open issues and one click from filtering the ledger. Below that, three kinds: what we asked the provider to fix, what changed after sign-off (information, not a decision), and what never passed intake. Nothing here decides whether a value is applied — provider values always go downstream. Marking an issue is how we ask for a correction; the next push is how it lands. What counts as an issue✕
An issue is a fault in the data at its source. The console records it and asks the owner to fix it — the value itself never changes here.
Missing critical fields

Nothing arrived where a customer-facing field must exist: street address, postal code, opening hours, sweeper. Blocking by default — a store cannot go live on a guess.

Inaccurate data

A value exists and it is wrong: incorrect, inconsistent, out of range, duplicate, stale, or badly formatted. Some block a sign-off, some only warn — the severity says which.

SeverityBlocking stops a new sign-off. Warning does not. Neither takes a live store offline — going down is always one click, going up is a check.
ClosingAn issue closes by itself when the next provider run delivers a value that changed and is valid — but only for missing / format / inconsistent / out of range. Incorrect, stale and duplicate always come back to a human.
