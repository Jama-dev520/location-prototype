Location Management Admin Console

One console for every location our customers can see — partner pickup points, lockers, package hubs and our own self-operated stores. It answers four daily questions in seconds, and it never edits the data it shows.

1Four jobs, and why the console looks like this

#What someone needs to doWhat “done” looks like
J1Find out which locations are liveStatus = active + Downstream = Live, count on screen, export exactly that set
J2Know who actually collects parcels (sweeper)On the row and in the detail page, filterable — no spreadsheet
J3Get a wrong address fixedReported to the data owner with a precise reason; fixed at the source, arrives with the next sync
J4See what changed, and whenAny field: who, when (to the second), old → new

These four jobs forced the architecture: J2 is a fact about the vendor record, J3 is a judgement about the OC record, J1 is the intersection of the two, and J4 has to cover all three. Hence two lists, not one.

2The model

Sources

LMS · packagehub PUDO Inc · point / locker M&MP · self-operated
→

Vendor layer

Read-only mirror of what was sent. Every field, including sweeper. Nothing here is editable.

→

Two gates

Intake check (fails → no OC record). Duplicate check ≥75% → hold for a decision.

→

OC layer

One customer-facing record per store. Only two writes: enable and flag.

→

Downstream

Visible iff the vendor record is active and the operator enabled it.

Quality loop: a wrong value is flagged on the vendor record → the owner fixes the source → the next sync brings the correct value → the change shows as drift against the signed-off baseline.

Choosing a Source rebuilds the Type filter from this table, so an impossible combination cannot be expressed. A record whose type does not belong to its source is marked type ≠ source and isolatable with one filter — a signal about the feed, not something we correct by hand.

One store, several vendor records

When a duplicate pair is confirmed as the same physical store, two vendor records feed one OC location (mapping 2:1). Each field is resolved independently:

M&MP (self-operated) → LMS → PUDO Inc. The first source with a value wins; the next fills the gaps. Every field in the detail page shows its source, so “why does this say X?” is answerable without asking anyone.

One visibility rule

A location is visible to customers iff its vendor record is active and the operator has enabled it. status comes from the source; is_enable is our decision.

3What an operator can do — two verbs

Enable — a sign-off, not a switch

  • An active vendor location feeds this store
  • Opening hours are present
  • Intake checks passed
  • No duplicate pair waiting
  • No open blocking data issue

All five pass → the dialog shows the customer-facing values with their source, plus an acknowledgement. Confirming captures a signed-off baseline. Turning a location off is one click — going offline is always safe.

Flag a data issue — the replacement for editing

Fieldopening_hours
Sub-fieldSATURDAY, address_line2
TypeMISSING INCORRECT INCONSISTENT OUT_OF_RANGE DUPLICATE STALE FORMAT
Severityblocking stops a sign-off · warning does not
Reasonmandatory, free text

Lifecycle: open → reported → fixed. The fix arrives with the next provider sync — and when it does, the issue closes itself: a changed and valid value closes it (closed_by = AUTO_SYNC), a changed but still-invalid value keeps it open, and only machine-checkable types qualify. Incorrect / stale / duplicate always come back to a human.

There is no edit button, and that is the design. Field locks, unlock reasons, per-field revert and accept/reject of provider changes all existed to make manual edits safe. Remove the edit, and they have nothing left to protect — while every value downstream can still be traced to one source record.

4After go-live

Provider values keep flowing and always reach downstream — the console never decides whether a change is applied. There is no accept, reject or re-sign step anywhere. What it keeps is the signed-off baseline, so it can answer one question: what moved since we signed this off? That shows as drift on the list row, in the detail page and in Data Issues. The only action is to flag a move that is wrong.

Hand-off, not workflow. The issue ledger exports to CSV — id, both location ids, field · sub-field, type, severity, reason, who raised it and when — so it can go straight into a ticket with the provider. That is the point of marking something, and it is why the console does not need an approve step.

8Questions this usually raises

Why not let operations fix the address?

Because then two systems hold different addresses and neither is authoritative. A flag with a reason reaches the party who can actually fix it, and the fix lands everywhere at once.

What if a provider is slow?

The issue stays open and keeps blocking new sign-offs if it is blocking; locations already live keep serving their current values. Nothing changes silently.

What about a store that genuinely moved?

The provider updates the record; the next sync brings the new address, it shows as drift against the baseline, and the operator re-signs. Two clicks, full trace.

Can we see who did what?

Yes — every action writes an audit row with actor, timestamp to the second, field, old value and new value.
